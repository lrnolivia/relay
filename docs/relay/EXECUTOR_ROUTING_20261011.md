# Configured executor routing

The existing Relay 2.0 rebuild assignment preserves the original 1.9 acceptance. This implementation selects and invokes one explicitly configured local or SSH executor for an existing queued job. It does not discover devices, create credentials, start another chat, or establish remote execution proof by itself.

`scripts/relay-dispatch.mjs` supports `probe`, `run`, and `dispatch`. Each host already needs the authorized Relay connection in its own environment, an authenticated Codex CLI, the exact clean assignment checkout, the dispatcher/executor code, and a private executor configuration. SSH uses existing host trust and batch authentication, disables forwarding, and does not send local credential environment variables to the remote host. Configure remote credentials separately only with applicable authorization.

Invoke `node scripts/relay-dispatch.mjs dispatch /absolute/routing.json /absolute/new-routing-receipt.json`. The routing file contains `project`, `assignment`, `owner`, `branch`, `job_id`, and a `hosts` array in preference order. Each host has `id` (matching its executor configuration's `executor_id`), `transport` (`local` or `ssh`), and absolute `node`, `script`, `config`, `workspace`, and `state_directory` paths. SSH additionally requires an existing `destination` host alias or user@hostname. `script` names this dispatcher on that host. Do not put secrets in the routing file.

A bounded, read-only probe checks the actual broker job, checkout repository/branch/head/cleanliness, executor lock, installed CLI and native source-protection support when enabled. Source-protected jobs also preflight their actual bounded source bytes. The host reports observed capabilities; the dispatcher checks every required job capability and its exact identity before selection. Failed probes have redacted unavailable reasons. Configured order breaks ties, rather than response timing. A successful probe does not prove model-account readiness or future process execution.

The dispatcher refreshes job revision/identity after probing, persists its selected host before launching, and invokes the same protected executor lifecycle. The executor rechecks admission and acquires the existing CAS lease. No alternate host is launched after any uncertain invocation, disconnected SSH session, failed status read or unaccounted exit. Inspect the durable broker, private routing receipt, original executor journal and process before explicit recovery. Never delete receipts or reuse a new receipt path as a substitute for that reconciliation.

The routing receipt is created exclusively with mode 0600 outside local source checkouts and through non-symlink parent paths. It contains no prompt, credential or raw process output. A terminal broker receipt attributed to the selected executor is recorded as accounted; neither that receipt nor exit code declares the assignment complete. Process evidence remains in the executor's existing private journal and protected checkpoints.

Focused tests cover deterministic selection, missing capability/unavailable host rejection, changed source/owner/revision, read-only real Git probes, lock refusal, SSH quoting/trust/forwarding constraints, private exclusive receipts and no retry after uncertain launch. These tests do not prove a real remote host ran. Live local routing, remote parity, worker acknowledgement and real away-window Night Shift remain separate acceptance evidence.

## Explicit feedback acknowledgement

An executor configuration may enable `feedback_acknowledgements: true`. The child receives a per-process request format in its context, alongside the read-only inbox. Only a standalone completed agent message with the matching nonce, report ID, revision and SHA-256 of the exact original text requests acknowledgement. Tool output, quoted JSON, inbox publication and ordinary reads do not request it. The child still receives no Relay credential or adapter-state write access.

The adapter requires an available published inbox page, then rereads the exact report and checks ownership, branch, current source, applicability, revision and original text before sending the existing CAS-protected acknowledgement. It saves the exact operation in its private journal before dispatch. Unknown outcomes block further acknowledgement writes; a resumed executor only checks for the matching server receipt, without automatically replaying a write. Unresolved receipts require explicit reconciliation. At most 32 acknowledgements are retained per journal.

Acknowledgement means an authenticated caller reported seeing the text. It does not establish native delivery, incorporation, a fix or objective completion. Focused tests include an actual synthetic subprocess request and source checkpoint lifecycle; real user feedback and remote-host consumption require their own evidence.

## Bounded Night Shift coordination and accounting

`node scripts/relay-night-shift.mjs /absolute/plan.json /absolute/new-private-receipt.json /absolute/stop-file` runs one admitted pass over one to eight exact existing protected-source jobs. It uses the existing authorized `RELAY_MCP_TOKEN` connection and configured executor hosts. It creates neither credentials nor a scheduler. The plan requires `schema: 1`, `enabled: true`, `operation: "code"`, a bounded `authorization` statement, and an `away_window` with explicit start/end timestamps spanning at most 24 hours. Each job supplies `project`, `assignment`, `owner`, `branch`, `job_id`, `summary` (at most 2000 characters), and its configured `hosts`.

For each project, `oversight[project]` must identify an existing separate oversight `assignment`, `owner`, `branch`, and exact `job_id`. The oversight owner and assignment must differ from the coding job, and the oversight execution cannot be any job in the coding plan. The canonical Night Shift ledger must already bind that same assignment. The coordinator checks the exact oversight execution's running state, concrete process receipt and unexpired broker lease before dispatch, immediately before launch, and while the coding job runs. A valid assignment lease alone is insufficient. These are authenticated executor reports; independent process verification remains separate. A missing or expired oversight executor stops admission or requests cancellation of the exact running coding job.

Completed dispatches now have an explicit accounting path to the existing Night Shift ledger. If the declared window has not ended, the private receipt records `accounting.state: "waiting-for-window"`. After it ends, run `node scripts/relay-night-shift.mjs account /absolute/plan.json /absolute/existing-private-receipt.json`. This command cannot launch a process. It opens the original private receipt under an exclusive accounting lock, checks exact terminal job identity and timestamps, persists each ledger intent before sending it, and confirms the item by canonical paginated readback. The ledger service independently checks the execution's process/source/evidence receipts and source commit. A missing response is reconciled through readback; an absent or conflicting item leaves the original intent for reconciliation without replaying the write or dispatching another job. A retained accounting lock after a crash also requires inspection before another attempt.

Neither accounting nor a terminal broker state verifies Lauren's absence, independent host process state, recipient acknowledgement or objective completion. A real declared window, existing authorized transport and actual oversight executor must be supplied before operational use. The 2026-10-20 integration tests use the real ledger service and MCP client with synthetic process/source fixtures; they do not establish a live away-time run. Relationship curation and private credential handoff remain separately gated.

### Native desktop oversight bridge

An existing first-class oversight chat may be represented by a job requiring only `native-thread-oversight-v1`. This capability cannot be mixed with coding or source-checkpoint capabilities. Its host bridge must inspect the actual exact owner chat through supported native host tools before every observation. It reports `checkpoint.native_thread` containing that `thread_id`, `host`, `state: "active"` and `observed_at`. The broker accepts only observations of the job's exact owner thread, at most 60 seconds old and no more than five seconds in the future. After leasing and saving the first observation, start with `process.adapter: "codex-desktop-oversight"`, the exact `thread_id`, matching `host` and an actual host/runtime `version`; omit `pid`. A native chat is not an OS child process and must never receive an invented PID.

Keep the observation fresh while the host independently reports the chat active. Idle, completed, failed, cancelled or unavailable native state is not an active observation: stop renewing it, cancel the exact coding job if necessary, and account for the native job separately. The coordinator rejects missing, stale, future, wrong-thread or wrong-host observations even if the broker lease remains valid. Coding jobs still require the `codex-cli` adapter and a concrete PID; native receipts cannot start coding work. A broker receipt remains an authenticated host report with `process_verified: false`; retain the actual host-tool readback separately. This bridge reuses an existing authorized connection and grants no new credentials, ownership or chat-control authority.
