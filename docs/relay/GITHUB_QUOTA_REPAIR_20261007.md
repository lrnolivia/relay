## Implemented boundaries

- One process-local reader retains at most128 authenticated representations and16MiB, with a4MiB per-entry ceiling. Cache keys include credential scope and complete request URL. Values are copied for each caller; oversized responses are returned whole without retention.
- Default authority/control reads always revalidate upstream. Only the Runner's authenticated HTTP progress display explicitly opts into15-second reuse and concurrent identical-request sharing. Writes invalidate before and after dispatch; older in-flight reads cannot repopulate the cache. Authentication and permission failures invalidate retained data without identity fallback.
- Conditional requests send the matching ETag and handle304 using only that authenticated cached representation. No-store and responses without ETags cannot retain an older display value. Bodies, writes and job-log reads are not cached.
- Token discovery/mint is shared during concurrent acquisition for the same repository and App credentials. Installation quota deadlines use the App and installation identity across repositories and token renewals. REST core and GraphQL primary buckets are separate; secondary cooldowns apply to both. Exhaustion, including a successful response with remaining0, blocks upstream requests until the actual reset or Retry-After deadline. Missing deadlines use a bounded60-second pause; no automatic retries are added. A full128-entry cooldown ledger conservatively pauses rather than forgetting a denied budget.
- Success and failure observations retain sanitized limit/remaining/used/reset/resource headers where supplied, request/cache/coalescing/304/blocked counts, and observation times. Progress results report logical versus actual transport activity and cache age. Diagnostics contain no tokens, response payloads or raw credential scopes. Custom transports without observations are labelled unobserved.
- The Runner HTTP error response exposes typed quota failures and an actual retry timestamp/Retry-After. Plain permission403, Access, Origin checks and write authorization remain intact. The existing explicit Runner-token identity stays selected for routes that previously used it.
