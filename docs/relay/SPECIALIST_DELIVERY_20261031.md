# Specialist delivery through the coordinator

The user requested actual specialists participating in ordinary work. Staff registry bindings remain routing, never proof of contribution. Existing worker instructions forbidding agent creation and reassignment remain intact.

## Coordinator activation

Runner preflight and resume now carry `specialist_workflow`. The interactive coordinator must establish the complete authorized acceptance plan and actual task-specific verifiers, choose relevant stage roles, admit missing supporting roles with canonical owner/CAS readback, and run the existing native continuity adapter. No acceptance plan or verifier command is inferred from arbitrary prose. Stage defaults are implementation → builder, test/review → verifier, runtime → reliability lead, ship → release captain; an explicit `specialist_role` selects a more relevant responsibility and requires actual specialist execution even when a verifier was already green. Record this field for promised specialist reviews. Trusted command stages do not pretend to be staff executions.

The native coordinator persists launch intent before invoking its authorized host subagent tool. It records the returned agent identity, exact request/operation/source/record and canonical staff/home team before any named running observation. Actual result identity must match. The receipt is coordinator-attested evidence of the actual host invocation, not independent proof supplied by an agent-ID regex. Recovery reads that same identity and never creates another worker to replace an uncertain launch. It preserves the real observation time and retains ownership only when the recorded source/input proof still matches; changed or unproven bytes lose attribution. Native tools must actually be available; the file channel is not a daemon or an agent launcher.

The CLI continuity coordinator assigns the bounded responsibility to a new canonical job and observes acknowledged executor start/finish RPC responses. Exact job, attempt, executor, process, owner, branch, source, revision and timestamp must agree. Successful process exit publishes awaiting verification, not completed acceptance. The existing verifier alone can mark a step passed.

## Ordinary CLI entry

`runExecution` is now the coordinator used by the existing dispatch entry. The bounded implementation is `runSingleExecution`; its prohibition on recursive delegation is unchanged. An explicit private `config.continuity` still supplies the full acceptance plan. For ordinary no-plan work, the coordinator preserves the exact existing queued job/request/provider/head and records only two real stages: run the assigned worker, then independently review current work. This checklist is explicitly partial (`complete: false`, `completion_scope: subobjective`), and its success never completes the assignment or substitutes for task-specific acceptance, merge or release checks.

The coordinator uses canonical owner/CAS amendment and readback to add a relevant reviewer while preserving existing staffing and scope. Explicit design, architecture, release, maintenance, research and QA categories select design editor, architect, release captain, reliability lead, researcher and verifier respectively. Otherwise the first canonically requested supporting review responsibility (including integrator) is used; generic or unknown scope receives general verification without inventing specialist requirements from prose or filenames. If the selected person is the lead, the coordinator uses a distinct verifier (or architect when the lead is the verifier). Only one bounded review is added automatically; multi-specialist acceptance stages require the actual private plan. This is routing until acknowledged process receipts establish actual work. The reviewer runs in a separate CLI session under the same bounded assignment. It must inspect actual source, stay read-only, and return a bounded structured verdict bound to the initial job and full source fingerprint. The verifier checks the actual transcript digest, canonical terminal job, session identity and unchanged bytes; missing, stale, forged or failed verdicts do not pass. A green process alone only verifies that the assigned process ran, never that the original objective is fulfilled.

`ordinary.json` preserves bootstrap, staffing intent and original job binding outside source. Existing legacy executor receipts/locks require explicit reconciliation before migration. An explicit `config.resume` with the original receipt preserves the legacy exact-session recovery route and returns `specialist_workflow_pending`, not a false specialist success. Lost staffing responses are read back, never blindly replayed. Lost finish acknowledgements are reconciled against the exact canonical operation/revision, result and saved transcript/source proof; historical terminal observations retain their original timestamps. Existing public priorities cannot be replaced without their matching private plan. A changed source/owner/provider/objective or conflicting initial job stops reuse. The original dispatch job remains the dispatch accounting identity; the canonical card and private coordinator result separately expose review success/failure. Dispatch accounting is not assignment completion.

## Ordinary native MCP handoff

Ordinary native chats use the discoverable `relay_runner_delegate` tool, not a standalone CLI token or a repository-local Node process. Initialize instructions, coordinate responses, preflight and resume direct the current coordinator to this lifecycle. The server records and validates the handoff; only the current host can invoke its actual authorized subagent tool. Workers retain their no-recursive-delegation restriction.

1. Read current ownership, source and controls. Choose one bounded existing step and an already admitted specialist role. Preserve any private acceptance plan. Retain the exact bounded prompt locally and compute its SHA-256 intent digest; send only the digest and a plain step label, never prompts, transcripts or secrets. If this host lacks authorized delegation, report the capability gap explicitly.
2. `prepare` uses a stable operation ID, owner, current record SHA, source SHA, objective digest, step/role and actual host-tool name. It atomically saves immutable project/assignment/owner/branch/source/objective/scope/staff bindings and a pending card step. Only the first confirmed response with `launch_required: true` permits one host launch. Fresh post-write control, source, policy and coordination readback must agree. Immediately before the host call, the coordinator checks current source, controls and ownership again.
3. Persist the packet locally, invoke the actual authorized host tool once, and retain its returned agent ID. Report `started` with that exact ID, request digest, source and actual observation time. This atomically records the identity and running card receipt.
4. Report the exact agent's result using `result`, its state and a SHA-256 digest of the privately retained actual result. A successful result is shown as blocked awaiting separate verification, never passed acceptance or objective completion. Failed/blocked/cancelled results remain distinct. Task-specific acceptance verification remains with the established verifier/publisher.

`read` reconciles existing state and never returns launch permission. A prepared intent without a known host launch outcome remains reconciliation-needed indefinitely: neither timeout nor a duplicate prepare authorizes another launch. Recover the original agent identity through this task's actual host receipt; do not inspect unrelated chats. Exact phase duplicates return the original receipt/timestamp without another write, while conflicting reuse rejects. Missing start, mismatched identity, changed source/objective/scope/routing, expired ownership or control holds stop new publication. Historical receipts survive rollover and cannot promote stale ownership. Post-write uncertainty preserves the saved intent while withholding launch permission.

The handoff and card projection are one canonical coordination CAS and independent readback, using the existing owner/policy/engine/commit-attribution controls. It does not directly write storage, silently add staff or erase existing priorities. Existing private-plan steps must already be recorded; labels, dependencies and prior receipts are preserved. A native-created no-plan checklist is explicitly partial. The bounded handoff history holds at most 16 operations per assignment and has no destructive reset operation.

Agent IDs and result hashes are coordinator attestations of actual host invocation, not cryptographic independent proof of execution. Synthetic tests establish validator/transport behavior only. Release acceptance separately requires live MCP `tools/list`/connector discovery, a callable endpoint, an actual authorized host launch, canonical running/result readback and the resulting live card identity. A cached connector catalog is not evidence that a newly deployed tool is callable, and local DOM captures do not establish native host mounting.

This native MCP protocol is specifically non-mutating snapshot review, research and inspection. A specialist must inspect the exact `source_sha`, not uncommitted work, and must not edit source or advance the branch. Source changes before result require reconciliation; the coordinator must not weaken the binding or relabel new bytes as the original snapshot. Source-mutating stages continue through the separately configured continuity/executor workflow. The release proof must use a useful real read-only specialist task.

Only an acknowledged winning CAS may issue `launch_required`. A failed/timed-out write whose bytes match on readback remains non-launching, including a losing identical 409/422 write. This avoids two callers receiving permission for the same same-millisecond intent. Successful specialist results carry a bounded `awaiting-verification` receipt phase: v24 cards display that wording while retaining the unverified blocked state and zero invented passes; genuine blockers retain their existing labels. v23 and earlier resource aliases remain served.
