# Goal-preserving acceptance expansion

Canonical policy is [Bible section6.1.1](../../LOEW_CHAT_BIBLE.md#611-goal-preserving-expansion); the shared proposal contract is `packages/runner/src/continuity-expansion.mjs`. This document describes implementation and configuration rather than a second policy.

A worker or coordinator can propose `necessary` supporting features/dependencies or `strengthens` improvements directly related to its original feature. Each bounded proposal records a stable id, immutable original-goal digest, reason, relationship, original criterion coverage, target feature stage, dependencies, added acceptance, implementation paths, description and an existing trusted verifier-profile name. It contains no executable command or permission/spending grant. The executor harvests explicitly marked `RELAY_CONTINUITY_ADDITIONS` JSON reports and stores them in the broker's exact job result; the coordinator can also ingest operator-supplied proposal data. Unknown process/job results reconcile before the same proposals are consumed.

The coordinator journals proposals before review. Its trusted semantic-review binding (the current native coordinator, or a configured standalone command) receives the original goal/criteria/authorization and proposal on stdin and returns an explicit structured verdict: goal preservation, authority, sensitive-permission/spending boundaries, canonical deduplication key and reason. This review may use an already authorized model/agent service; workers cannot select it, approve themselves or substitute a string assertion for review. When no reviewer is configured or a decision is inconclusive, the addition stays visible and dependent promotion waits. This is a semantic capability limit, not a request for Lauren to approve each ordinary related improvement.

Admitted additions become real stages and criteria in the persisted effective plan. Necessary dependencies gate their target; all new work gates review/shipping/runtime. The original base plan, original goal and acceptance remain unchanged. The coordinator schedules the combined DAG, executes supporting work, verifies its new acceptance and invalidates affected earlier evidence. A late discovery cannot be discarded merely because the original finite list passed.

Configuration extends the existing `continuity` plan with `expansion`: `enabled:true`, scoped `authorization`, `original_goal` matching the canonical assignment, and named `profiles`. Each profile supplies a kind (`implementation` or `test`), complete relevant verifier `inputs`, `verify` argv and optionally an existing trusted `command`. `review` is the trusted semantic-review argv for standalone CLI use. The native adapter supplies review through the existing current task instead; the native acceptance fixture configures real verifier profiles and needs no reviewer process or bearer token. See [native activation](NATIVE_CONTINUITY_20261020.md). `allowed_paths` may declare a previously authorized expansion envelope; it grants no host permission and cannot override canonical ownership. Defaults/hard bounds are8 cumulative additions, depth2 (maximum3),32 proposals and32 total stages, with16 execution actions per pass and the existing two-identical-attempt repair budget. Smaller budgets can be configured. Reaching a bound records a visible wait and leaves affected completion/promotion open; it never creates an unbounded new queue.

For new paths, the adapter uses Relay's existing revision-checked additive amendment transaction on the same assignment and branch, preserving resources, the original goal and acceptance history. The canonical acceptance gains a structured supporting-feature receipt with its new criteria, review and profile identity; it is not left only in the local journal. It journals the original scope request before sending it, reads canonical scope back after a lost reply, and never overwrites a later withdrawal or another owner's reservation. An unauthorized path, protected credential/config store, overlap, changed goal, sensitive permission or paid service stays parked for its real authority. User/security/global stops and source/control revisions are checked before review, admission and execution.

Exact proposal replay and semantic duplicates do not create another stage. Dependency cycles, changed proposal identities, corrupted journal data and goal drift are rejected with durable reasons. Expansion budgets and ledger state survive resume. An explicitly enabled expansion policy can migrate an unchanged legacy base checkpoint; unrelated base-plan/environment changes still require checkpoint reconciliation. Trusted profile inputs are measured along with actual environment/toolchain inputs, so supporting evidence is not reused after relevant changes.

Codex and Claude use this same contract. Their CLI adapters have distinct capability requirements, process/session formats and immutable receipt identities. Switching providers does not restart a pending job or permit concurrent writes. A native desktop thread is not inferred from a CLI session or process.
